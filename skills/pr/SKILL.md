# Prepare PR with Context

## Overview
Generates a complete pull request description by reading branch references, analyzing changes, and calculating blast radius. Produces a structured PR document in `.ccs/pulls/` and outputs a ready-to-use PR description. All analysis uses local git commands — no GitHub API.

## When to Use
- Feature branch is ready for review
- Need a structured PR description with impact analysis
- Want to review changes before creating the actual PR
- Preparing merge documentation

## Instructions

### Step 1: Identify Source and Target
1. Get current branch: `git rev-parse --abbrev-ref HEAD`
2. Target branch: user-provided or default to `main`/`master`
3. Read `.ccs/branches/<current-branch>.md` if it exists
4. If branch ref is stale or missing, regenerate it (same as `/ccs-branch switch`)

### Step 2: Gather Change Data
1. `git log --oneline <target>..<current>` — all commits
2. `git diff --stat <target>...<current>` — files changed with line counts
3. `git diff --shortstat <target>...<current>` — totals
4. `git shortlog -sn <target>..<current>` — contributors
5. `git log --format="%h %s" <target>..<current>` — commit messages

### Step 3: Analyze Impact
1. Read `.ccs/file-index.md` — rank changed files
2. Read `.ccs/project-map.md` — identify downstream dependents
3. Read `.ccs/architecture.md` — understand module boundaries
4. For each changed file:
   - Note its rank and role
   - Find downstream dependents via Grep for imports
   - Check if it crosses module boundaries
5. Categorize changes: feature, fix, refactor, config, docs

### Step 4: Identify Review Areas
Based on file ranks and change types:
- **Must review:** S-rank files, files with 50+ line changes, shared utilities
- **Should review:** A-rank files, cross-module changes
- **Quick check:** B/C/D-rank files, config changes, docs

### Step 5: Generate PR Document
Create `.ccs/pulls/<branch-name>.md`:

```markdown
# PR: <title derived from branch purpose and commits>

> Generated by codebase-context-skill | <timestamp>
> Branch: <current-branch> → <target-branch>
> Status: draft | ready
> Created: <date>

## Summary
<2-3 sentence summary derived from commits and branch purpose>

## Changes
| File | Action | Lines Changed | Rank | Impact |
|------|--------|---------------|------|--------|

## Blast Radius
- **Direct changes:** N files
- **Downstream dependents:** N files
- **Breaking changes:** none | list

## Commits (<count>)
| Hash | Message | Author |
|------|---------|--------|

## Review Areas
### Must Review
- `src/auth.ts` (S-rank, +45 lines, 8 dependents)

### Should Review
- `src/middleware.ts` (A-rank, cross-module)

### Quick Check
- `src/types.ts` (C-rank, type additions only)

## Review Notes
<auto-generated notes about patterns, risks, and things to watch for>

## Test Recommendations
- [ ] Run existing test suite
- [ ] Test <specific area affected by changes>
- [ ] Verify <edge case related to changes>
```

### Step 6: Output PR Description
Also output a clean PR description ready to paste into GitHub/GitLab:

```markdown
## Summary
<summary>

## Changes
- <bullet list of changes>

## Test Plan
- [ ] <test steps>

## Blast Radius
- N files directly changed
- N downstream files may be affected
```

### Step 7: Track in task.md
```markdown
## Task #{number}: PR — <branch> → <target>

**Timestamp:** {now}
**Status:** done
**Type:** pr

### Details
- **Branch:** {branch} → {target}
- **Commits:** {count}
- **Files changed:** {count}
- **Blast radius:** {count} downstream
- **PR doc:** `.ccs/pulls/{branch-name}.md`
- **Review areas:** {must: N, should: N, quick: N}
```

## Token Efficiency Rules
- Read branch ref first — it has most of the context already
- Use `--stat` and `--shortstat` instead of full diffs
- Dependency walking capped at 1 level (direct dependents only)
- Don't read every changed file — use Grep for import analysis
- For large PRs (50+ files), summarize to top 20 by rank

## Limitations
- Does not create the actual PR on GitHub/GitLab — outputs description only
- Blast radius is estimated from static import analysis
- Review area recommendations are based on file rank, not code complexity
- Does not run tests (use `/ccs-test` separately)
